# Proposal: compress-pdf

## Why

用户要发 PDF（微信/邮件/打印），体积常常超标；「图片工坊」已能把图片压小，PDF 却只能拒收。
PDF 体积大头通常是内嵌图片（扫描件尤甚），只做无损结构优化收益有限（实测 5–30%，扫描件更低）。
目标：**支持导入 PDF 并压缩其文件大小，且内容不能变不清楚**（用户原话，即质量下限是硬约束）。

## What Changes

- 导入链路新增 PDF：`internal/imageproc` 格式注册表加 `.pdf`（内容嗅探 `%PDF-` 头，扩展名只作预筛——沿用现有图片的探测哲学）。
- 新增 PDF 压缩管线（两级，串行）：
  1. **图像重压缩**（主要收益）：遍历 xref 表定位图像 XObject，对「单一 DCTDecode、DeviceRGB/DeviceGray、8bpc」的图像用标准库重编码 JPEG（质量下限 75、**不缩小像素尺寸**），仅当结果更小时替换；其余滤镜（Flate 图像、JBIG2、CCITT、JPX）跳过并计数。
  2. **无损结构优化**（pdfcpu optimize）：去重内嵌资源、对象流/xref 流压缩、清理无用对象——内容字节级不变。
- 三条规则（转格式/压到指定大小/限制尺寸）**对 PDF 全不适用**：纯 PDF 批次时规则区禁用并说明；混批时规则只作用于图片项。
- 图片 + PDF 混批同队：逐项按类型分流（图片走三条规则，PDF 走压缩管线），共用现有状态机、暂存区、下载命名（`<原名>-out.pdf`）与历史记录。
- 逐项消息诚实汇报：替换了几张图、跳过几张及原因；全部跳过且结构优化收益 <1% 时标「无需处理（PDF 已经很紧凑）」。

## Spike 证据（2026-10-24，/tmp/pdfspike）

用 pdfcpu v0.16.3 模型 API 完整走通：定位 2400×2400 DCTDecode 图像（xref 表中为**值类型** `types.StreamDict`，改后整体写回条目）→ `image/jpeg` q75 重编码 → 回写 → `api.WriteContextFile` 落盘。结果：图像数据 238KB→136KB，整文件 **-42.9%**，`api.ValidateFile` 通过，渲染前后像素对比平均差 0.41/765（0.05%，肉眼不可辨）。纯 Go、无 CGO，符合 ADR-0004。

## Non-goals

- 不做 PDF→图片/图片→PDF 的格式互转（「转成哪种格式」语义不扩展到 PDF）。
- 不做目标体积搜索（无可调参数空间可搜，诚实禁用而非假语义）。
- 不做空间降采样 / DPI 下限（v1 保持原像素尺寸重存；后续版本再评估按页面显示尺寸算 DPI 下限）。
- 不碰加密与签名 PDF：检测到即失败并说明（不解密、不破坏签名法律效力）。

## 决策记录

范围三问已于 2026-10-24 与用户确认：深度=一步到位含图像重压缩；规则映射=三条全不适用；混批=同队分流。选型决策见 `docs/adr/0009-pure-go-pdf-compression.md`。
